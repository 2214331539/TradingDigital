# ChatAI 技术架构与技术栈选型

## 1. 技术目标

第一版系统需要满足以下工程目标：

- 支持 ChatGPT 风格的实时流式对话。
- 支持企业内部账号、角色、权限和后台管理。
- 支持模型供应商可配置，不把业务逻辑绑定到某一家模型 API。
- 支持后续扩展知识库、工具调用、企业数据查询，但第一版不实现这些模块。
- 支持桌面端高质量体验，并保证移动端基础可用。

## 7. 模型 API 接入设计

### 7.1 统一模型网关

后端不在业务代码中直接调用具体模型供应商，而是通过 `ModelGateway` 统一封装。

```text
ChatService
  -> ModelGateway
    -> ProviderClient
      -> OpenAICompatibleClient
      -> AnthropicCompatibleClient
      -> CustomHTTPClient
```

第一版建议优先实现 OpenAI Compatible 协议，因为很多模型供应商都提供类似的 Chat Completions API 格式。

### 7.2 模型配置项

每个模型在后台可配置：

- 模型显示名称。
- 模型标识，例如 `gpt-4.1-mini`、`deepseek-chat`、`qwen-plus`。
- 供应商名称。
- Base URL。
- API Key 引用。
- 最大上下文长度。
- 最大输出 Token。
- 默认温度。
- 是否支持流式输出。
- 可访问角色。
- 是否启用。

API Key 不建议明文保存在业务表里。第一版可以存储加密后的密文，或只保存环境变量引用名，例如 `OPENAI_API_KEY`、`QWEN_API_KEY`。

### 7.3 流式响应

第一版使用 Server-Sent Events。

```text
POST /api/v1/chat/completions/stream
Accept: text/event-stream
```

事件类型：

|事件|说明|
|---|---|
|message_start|AI 消息创建成功|
|delta|增量文本|
|message_end|生成完成|
|error|生成失败|
|usage|Token 和耗时统计|

前端收到 `delta` 后逐字追加到当前 AI 消息，收到 `message_end` 后将消息状态改为 `completed`。

## 8. 认证与安全

### 8.1 登录态

- Access Token 有效期建议 15 到 60 分钟。
- Refresh Token 有效期建议 7 到 30 天。
- Refresh Token 支持服务端撤销。
- 退出登录时撤销当前 Refresh Token。

### 8.2 接口安全

- 所有业务接口默认要求登录。
- 管理端接口必须校验权限码。
- 普通用户接口必须校验资源归属。
- 密码只存储哈希。
- 模型 API Key 不返回给前端。
- 操作日志记录关键管理行为。

### 8.3 限流策略

建议第一版至少实现：

- 登录失败限流。
- 单用户每分钟消息数限制。
- 单用户每日消息数限制。
- 单次输入最大长度限制。
- 模型供应商调用超时控制。

## 9. 数据存储策略

核心数据存储在 PostgreSQL：

- 用户、角色、权限。
- 会话、消息、消息版本。
- 模型配置、助手预设。
- 分享链接、项目分组。
- 操作日志、登录日志、模型调用日志。

Redis 用于：

- Token 撤销列表。
- SSE 生成状态。
- 请求限流计数。
- 短期缓存。
